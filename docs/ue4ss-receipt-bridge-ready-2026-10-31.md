## Additive implementation

New source: `experiments/ue4ss-receipt-host`. A plain-C versioned interface permits the existing receipt adapter to call a separate standard C++ UE4SS mod synchronously on the existing owner/window thread. The request borrows the original guarded owner callback and binds the current pawn and copied-hint revision. It carries no AP receipt acknowledgement authority.

Only the experimental mixed-delivery consumable branch attaches this interface. The packet's original owner checks, lease, bounded sample/inventory reads and receipt state remain intact. Converter/grant calls go through exact UFunctions; the unchanged receipt core still requires precisely +1 of the requested item and no unrelated inventory changes before acknowledging it. A duplicate AP identity never reaches the converter/grant. Failure after entry remains uncertain, closes the original graph and is not retried automatically.

The interface never retains a game object or calls Lua to grant. It verifies the actual thread before invoking the original owner's thread guard, rejects context changes and reentry, uses typed 24-byte parameter frames, and consumes each grant entry before calling ProcessEvent. Interface failure does not enable the legacy grant as a fallback. Existing wardrobe, Zodiac, maps, stats, policy gates, local drops, save isolation and early Critical behavior are unchanged. Native bounded reads/signature guards are deliberately retained at this stage.

- `build/ue4ss-receipt-bridge-20261031`: Zig Normal/SelfTest C fixtures and fresh/resume Forest runtime overlays. All 67 unchanged receipt/adapter and new ABI-attachment tests pass. Normal builds expose no injected API or synthetic controls. Compared with their SQLite-fixed baselines, runtime exports only add the internal reflected adapter entry, with no missing baseline export.
- The actual game's BP_TresGetItem construction was audited at RVA 0x8204D0..0x82091F. Instructions at 0x820583 and 0x820593 supply C++ frame size 24 and flags 0x4022401. The constructor's 0xFFFF argument goes to +0xA4, not ReturnValueOffset. Finalization at 0xBFB370 clears NumParms at +0xA6 and initializes ParmsSize/ReturnValueOffset to 0/0xFFFF at +0xA8/+0xAA (0xBFB381..0xBFB388). It then counts parameters and sets ParmsSize to each field's unrounded end (0xBFB3DD..0xBFB3F2). The final one-byte bool at offset 16 therefore gives reflected ParmsSize **17**, while the owned aligned C++/C-interface frame remains **24** bytes. No ReturnParm field exists, so ReturnValueOffset remains 0xFFFF. The host checks 17, not the constructor's struct allocation size. The native one-byte bool construction is at 0x820686..0x8206C0. The three parameter names/types/offsets were independently observed in the earlier live metadata capture. The host reports this contract at context observation and revalidates it before every receipt call. A context hint can survive temporarily unavailable item metadata and never authorizes an award by itself. No item was awarded during this audit.
- A separate synthetic loader process proves exact loaded-module lookup from a Unicode executable path, refusal to auto-load an absent provider, and ignoring a loaded same-name decoy. It loads only fake providers and the effects-off C fixture, never the real host/framework/game. Assertions are explicitly enabled.
- Five readiness regressions confirm that missing, stale, wrong-PID or incomplete initialization logs cannot trigger attachment. A ready log only permits the unchanged authenticated StartupReader to run; it never creates or replaces startup authority. This is a private harness delay to avoid racing framework initialization, not a new production admission mechanism.
- Two cancellation/control-failure regressions confirm that the harness keeps its coordinator and runtime lease alive until simulated native cleanup finishes. A failed send cannot release the module while the game is still open.
- `build/ue4ss-receipt-acceptance-20261031/socket-test.json`: real localhost MultiServer/socket admission of empty history, one Hi-Potion receipt, and repeated Sync without a duplicate identity. No game preparation, mod installation, owner hook or test arming occurs in this check.
