### What explicit installation still requires

The current client `steam_launch_v187_candidate.prepare_launch` writes session readiness/resume records **and** installs the startup DLL/paks. Its `Installation.restore` removes owned additions on close. This explains why the current package is not yet a permanent, user-installed mod. Permanent code and per-launch session data need separate ownership; the client should verify installed code, write its clearly documented session data, and remove only that session data after closure. It must not delete user saves or silently replace other mods.

The early startup code already distinguishes three cases. No readiness file chooses vanilla mode once, without filename/Critical hooks. Valid prepared AP data chooses isolated storage before the game first reads saves. Invalid, stale or already-consumed AP data fails closed; it must not silently fall back to vanilla while the client claims AP is active. Starting the client after vanilla startup cannot safely switch storage mid-process; it must explain that a normal game restart is needed. Closing the client early must retain the active game's storage routing until game exit.

The fresh and resume startup sources differ only in the exported authority-check name and which authenticated mode enables it. A single permanent bootstrap supporting both is a plausible compatibility change, but still requires fresh/resume and rejection tests. Do not merely export both checks with shared unrestricted authority. The cooked menu/prototype paks also have behavior independent of the client; permanent installation needs an audit or an inactive gate for those assets. The native host's passive behavior alone does not prove the whole mod is vanilla-safe. Moving early storage into `on_unreal_init` remains unsupported because save discovery happens earlier.
